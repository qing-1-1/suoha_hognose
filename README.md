# Suoha Hognose

公开个体档案与私有繁育工作台。原生 HTML/CSS/JavaScript + Netlify Functions + Supabase，不需要前端框架。

**拍卖与收款（2026-10-08）：** 后台新增「拍卖管理」「收款码与审核」。普通购买或拍卖成交后展示店铺收款码，买家上传截图，中文 OCR 辅助提取付款信息，人工核实实际到账后更新销售状态。代码和本地测试已提供，尚未部署或执行线上迁移。

### 启用收款码与 OCR

如果 029、030、031 都尚未执行：保留已执行的 001–028，依次完整执行 **029 → 030 → 031**，每个文件成功后再执行下一个，最后部署当前代码。不要使用先前已删除的 `030_alipay_payments.sql`；当前 030 为 `030_manual_payments.sql`。这三个文件均包含事务和 PostgREST 接口缓存刷新，成功执行后不要重复执行。

新增两种付款渠道：执行 `supabase/migrations/031_wechat_transfer.sql` 后，在后台「收款码与审核 → 加微信转账」配置店铺微信号、收款人并启用；无需二维码。已有二维码渠道仍可独立配置。买家选择“加微信转账”或“直接扫码支付”，两者都提示打开支付详情，上传包含支付单号、金额、收款人及付款时间的完整截图。

1. 在 `029_auctions.sql` 后执行 `supabase/migrations/030_manual_payments.sql`，创建收款配置、付款记录和私有 `payment-media` 存储桶。沿用下述四个服务端环境变量；无支付宝接口、支付签约或云 OCR 密钥。
2. `npm ci` 安装锁定版本的 `tesseract.js`、中英文语言包和 `sharp`。`npm run build` 自动复制 OCR JS、WASM 和语言模型到 `dist/ocr/`；`npm run dev` 同样可加载。模型已经下载在本地依赖目录，部署时由本站分发，首次识别需要加载模型，之后使用浏览器缓存。不要只复制源 HTML，必须执行构建。
3. 后台「收款码与审核」上传真实收款码，填写收款人、付款说明并启用。支持微信、支付宝和其他收款码。图片保存在私有存储，买家只有在登录且拥有订单时才可获取短时收款码链接。
4. 明码标价的人民币在售个体显示「确认购买」；买家账号登录后确认订单并预留 2 小时。未标价个体继续询价。拍卖赢家共用同一付款流程，详情展示成交时自动弹出付款窗口，也可从「我的订单 / 竞拍」再次进入。
5. 买家提交付款截图，浏览器本地 OCR 提取金额、交易单号、时间、收款人，可手动校正。数据库分别保存处理后的截图、图片摘要、OCR 原文/字段/置信度、买家校正字段、收款配置快照、审核人/时间/备注。OCR 来自买家端，不能当作可信到账证明；后台必须查真实收款账户。
6. 后台查看截图和订单，填写实际到账金额并勾选已核实后确认，订单才变为已收款；退回须说明原因，买家可重新提交。存在待审核截图时不能直接取消预留、改价或绕过审核标记已收款。超时不自动释放库存，避免已付款但未审核时重复出售。

金额不一致会在后台提示；相同截图和已确认的重复交易单号有数据库拦截。网络失败重试使用相同提交编号。图片只接受 JPG/PNG/WebP，服务端重新编码并去除元数据；未完成数据库登记的上传可能留下私有孤立图片，可按保留期对照付款记录清理，不能直接删除在用截图。后台分批读取全部付款记录，待审核优先展示；买家订单和个人列表显示最近 100 条。

验收：`npm test`、`npm run test:ui -- tests/browser/payments.spec.js tests/browser/auctions.spec.js`。OCR 浏览器测试使用明确标注的测试样张和真实本地识别模型；订单及存储接口采用模拟数据，数据库用 PGlite。上线后还需用真实配置检查 Supabase Storage 权限、图片上传与后台到账审核闭环。

### 启用拍卖

1. 已部署至 028 的数据库，执行 `supabase/migrations/029_auctions.sql`。先在验证环境检查，再应用到生产。
2. Netlify Functions 需要已有的 `SUPABASE_URL`、`SUPABASE_PUBLISHABLE_KEY`、`SUPABASE_SERVICE_ROLE_KEY`、`INQUIRY_HASH_SECRET`（随机值至少 32 字节）。不新增第三方支付密钥，不把服务端密钥放进浏览器。
3. 部署后检查 Netlify 的 `auction-settle` Scheduled Function：`netlify.toml` 配置每分钟运行，仅生产发布自动调度；预览环境不会自动定时运行。运行一次并检查日志确认数据库连接及迁移正常。打开单条拍卖详情也会补做到期结拍，迟到出价始终由数据库拒绝。
4. 后台「公开展示」准备人民币计价、已发布、在售的个体。公开说明中写清运费和交付条件；到「拍卖管理 → 创建拍卖」配置起拍价、最低加价、开拍时间、无人首拍期限、临近截止延时间隔、可选强制截止上限及付款期限。
5. 买家从网页右下角「我的订单 / 竞拍」注册独立账号，填写微信或手机号。此账号与后台 Supabase 成员完全分离；不需要开放 Supabase Auth 注册。密码采用随机盐 scrypt 存储；会话为 HttpOnly、SameSite Cookie，生产使用 Secure，7 天过期。账号及 IP 有服务端频率限制。

### 拍卖行为与当前边界

- 首拍可等于起拍价；之后至少加一个最低加价金额。临近截止时，每次有效出价将截止时间延至「服务器当前时间 + 延时间隔」，不会缩短已有截止时间。默认不设硬性截止；仅卖家明确填写强制截止上限时才限制延时，并在前台公开提示。当前领先者不能自加价。
- 出价、结拍、普通销售预留按同一展示档案加锁。重复请求不会重复记账；拍卖期间拒绝新询价及普通预留，禁止直接修改价格、币种、发布和销售状态。后台可说明原因后取消未结束的拍卖，原因对参与买家可见；规则修改通过取消并创建新场次完成。
- 无人出价到期流拍；有出价则生成唯一的待付款预留。付款期限从系统实际创建预留时计算，后台仍需人工核实收款、交付、成交。到期未付款不自动释放，避免线下已付但尚未登记的个体被重复出售。取消预留后需手动重新上架才能再开拍。
- 详情每 5 秒刷新报价，倒计时按服务端时间校准；买家「我的竞拍」保留最近 100 场参与记录、赢家成交编号及销售状态。公开报价记录不含账号、联系方式或内部买家 ID。
- 第一版采用收款码转账和人工确认，没有支付平台自动回调、保证金、代理出价、短信/微信推送、手机号验证或自助密码找回。联系方式由买家自行填写，不等于已核实身份；上线运营前应明确店铺联系入口和违约处理方式。
- 测试：`npm test`；`npm run test:ui -- tests/browser/auctions.spec.js tests/browser/site.spec.js`。浏览器测试采用模拟数据；数据库事务测试采用 PGlite，不替代生产 Supabase RLS、Netlify 定时任务及真实多人网络环境的发布验收。

**动画与图片提速（2026-09-30）：** 首页喂食与出壳动画在可见时循环，离屏、后台或弹窗打开时暂停，遵循系统减少动态效果设置。目录批量签名公开图片，详情直达复用服务端数据；列表和相册小图使用最长边 640px 的 WebP，详情保留 1800px 展示图。先执行 `028_specimen_thumbnails.sql`，再部署代码；新上传／替换照片自动生成两种尺寸，旧照片在后台个体图库点击“补齐缩略图”逐个图库补齐。未补齐的照片继续使用原图。迁移与旧照片补生成均未自动运行于生产。

## 启用新功能

本次代码改造没有自动执行线上迁移、发布个体或部署网站。

1. 确认现有原始业务表、Auth / profiles / RLS 以及 `005–018` 迁移已经具备。
2. 在验证数据库依次执行以下增量迁移并核对后，再应用到生产：
   - `019_public_catalog_and_sales.sql`：展示配置、媒体、购买意向、销售状态和公开数据接口。
   - `020_breeding_operations.sql`：真实配种、窝次和幼体入库事务。
   - `021_acquisition_cost_history.sql`：保存现有购入成本快照，关联手工支出去重。
   - `022_route_move_transactions.sql`：路线移动的并发校验与撤销／重做支持。
   - `023_inventory_libraries.sql`：种群／自繁库归属及留存转库。
   - `024_listing_removal.sql`：公开展示删除与交易保护。
   - `025_breeding_calendar.sql`：预计日期、实际繁育记录与首页提醒。
   - `026_public_media_selection.sql`：逐张公开照片及年份／基因筛选。
   - `027_growth_and_batch_registration.sql`：成长记录类别、留存评估及批量登记事务。
   - `028_specimen_thumbnails.sql`：缩略图路径、公开读取权限和目录图片信息。
3. Netlify 服务端环境变量：`SUPABASE_URL`、`SUPABASE_PUBLISHABLE_KEY`。购买意向需要服务端 `SUPABASE_SERVICE_ROLE_KEY`，另需至少 32 字节随机值的 `INQUIRY_HASH_SECRET`；公开照片接口兼容仅通过公开读取策略签名的配置。这些私密值只配置在 Netlify Functions 环境，不能写入浏览器代码。AI 继续使用原有 DeepSeek 配置，详见 [.env.example](.env.example)。
4. 核对 Supabase Auth 的 Site URL / Redirect URLs，允许实际域名的 `/admin` 密码恢复入口。
5. 登录后台“公开展示”，新建草稿、编辑公开资料、上传真实照片，再主动勾选发布。

所有现有个体默认保持私有；迁移不会自动上架。后台显示功能不可用时，应先检查迁移与账号权限。公开目录连接失败会显示重试状态，不用假数据补位。

`019` 创建独立私有 Storage bucket `specimen-media`；执行 `026` 后，只有已发布档案中勾选公开的照片允许匿名读取，新照片默认私有。上传图片会生成最长边 1800px 的 WebP 展示副本，不更改现有原始图库。下架后公开媒体接口重新校验发布状态；已被第三方下载的图片无法追回。

## 当前边界

- 客户账户、在线付款、退款、自动到期释放、消息通知和自动交付没有启用；成交由授权成员人工核实记录。
- 预留到期显示待处理，取消恢复为仅展示，需要人工确认重新上架。已收款记录不提供直接取消入口。
- 客户联系方式仅存于内部意向记录，当前没有自动发信或第三方通知。
- 核心业务与工作区列表已改为分批完整读取，库/记录/发布列表各自分页显示，移除原 300/1000 条截断。当前仍采用完整快照，超大规模的按需服务端查询与独立聚合另行规划。AI 对话和分析的既有加载窗口不在此次改造范围内。
- 成本快照来自已记录的购入成本，不是已验证付款日期的会计凭证；既有重复支出需人工关联，没有按金额猜测自动合并。
- 路线撤销／重做仅针对本次会话的坐标移动；删除节点和改变谱系不会被隐式恢复。
- 配对比较最多四组，依赖现有独立位点假设；未实现连锁、联合携带分布及完整跨代自动搜索。
- 执行 026 后，前台筛选支持文字、系列、性别、销售状态、出生年份、单个原子基因及状态、价格排序；尚未实现多基因组合和价格区间。
- 分享元数据由生产 Netlify 详情函数输出；本地开发详情通过客户端渲染。
- 首页含用户提供的真实爬房、经过艺术处理的蛇照片和已标注的概念素材，公开个体仍读取真实后台资料，没有导入假在售数据。像素短片与替换方式见 [像素素材制作记录](docs/media/像素素材制作记录.md)。

完整的已完成清单、后续公开网站/内部功能任务、素材需求及验收标准见 [视觉升级与功能优化实施方案.md](docs/design/视觉升级与功能优化实施方案.md)。第一轮纯视觉修改无需新增 SQL；当前完整发布以本文上方启用步骤为准。


## 个体照片与公开图片修复

“个体档案 → 编辑个体”现已提供上传、替换、删除、封面、说明与拍摄日期编辑；与“公开展示 → 照片”共用图库。照片独立保存，首次上传只创建未发布配置，不自动上架。

公开图片现在先检查发布状态，再跳转到 Supabase 的 60 秒签名地址，避免原图 Base64 超过函数响应限制；兼容没有服务端密钥但已具备发布照片读取策略的环境。现有照片无需重传，Storage 仍是私有 bucket。本轮无 SQL 或新增环境变量，需要重新部署网站及 Functions。

首页还加入用户 HEIC 原片制作的特写，已注明背景艺术处理。详细排查证据、权限有效期和验收结果见 [实施方案第 9 节](docs/design/视觉升级与功能优化实施方案.md#9-追加交付公开图片修复个体照片编辑与蛇的特写)。
