## 两个项目现在实现的内容

- 服务端 HMAC-SHA256 签名、令牌获取及缓存；仅在只读请求遇到明确令牌失效时刷新重试。
- 设备白名单、状态/规格查询、原始数据点查看、每层温湿度绑定与单位缩放。
- 当前值有可信属性更新时间时按有效期区分正常/过期；只有标准状态值时显示“云端最新值，采样时间未知”。不会把查询时间伪装成采样时间。
- 目标温度与开关控制：必须显式配置控制映射且设备在线，服务端复核设备功能、数值范围及步进。目标温度通道与实际测温通道分别配置。
- 控制请求先入库，再访问涂鸦；保存操作人、请求号、设备、请求内容和结果。重复请求不会再次发指令；网络不确定结果标为 unknown，不能自动重发。
- 按设备列出已保存绑定的所有层，提醒操作的实际影响范围。

两端使用同一云客户端实现。此轮使用模拟涂鸦响应和隔离数据库验证，未取得真实云凭证、未向 A1 发过指令、未部署生产。后台没有自动温控循环、昼夜调度或自动化规则；本轮提供手动查询和手动设定。

## 授权与配置步骤

1. 在涂鸦开发者平台建立云项目，选择与涂鸦智能 App 账号对应的数据中心。按当前控制台流程关联 App 账号，让 A1 出现在云项目设备列表中。
2. 在 API 调试工具确认该设备可调用下述设备信息、规格和状态接口；按项目情况开通对应服务。权限、期限、额度与费用以实际控制台为准，本实现不承诺免费长期使用。
3. 在服务器配置 `TUYA_REGION`、`TUYA_ACCESS_ID`、`TUYA_ACCESS_SECRET`、`TUYA_DEVICE_IDS`。设备 ID 列表逗号分隔，最多 100 台；每次房间读取最多 20 台不同设备。同一进程有 15 秒设备缓存，手动刷新和多实例仍会消耗云 API 额度。
4. 部署代码及数据库迁移。进入 **爬房 → 温湿度设备 → 涂鸦设备、数据点与控制**，选择白名单设备，点击“读取设备”。
5. 核对设备数据点的名称、code、单位和 scale。将实际测温 code 填入对应层的数据通道，来源选“涂鸦云（A1 智能版）”，设备标识填真实设备 ID，保存绑定。湿度独立配置其传感器，不假设 A1 提供湿度。
6. 如需控制，先在数据点规格核实目标温度与开关的可写 code，再配置控制映射和明确的允许温度范围。最后设 `TUYA_CONTROL_ENABLED=true`。没有正确映射时界面不显示该控制按钮。

区域代码：cn / us / eu / in / us_east / eu_west；仅允许内置涂鸦 HTTPS 域名，不接受网页传入任意云地址。旧项目在 Netlify 配置环境变量；重构项目在 API 进程配置环境变量，本地 `.env.example` 不会自动载入。Docker 验证环境可叠加 `compose.tuya.yaml` 给 api 和 api-green 传入配置，不把密钥写入文件或前端。

控制映射格式如下。**其中设备与 code 为示例，20–32 °C 也只是格式示例，不是饲养建议或 A1 已确认规格，不能直接作为生产配置。**

```json
{
  "实际设备ID": {
    "temperatureCode": "实际目标温度code",
    "powerCode": "实际加热开关code",
    "minC": 20,
    "maxC": 32
  }
}
```

将此 JSON 作为 `TUYA_CONTROL_MAP` 的字符串值；可以只提供一种控制。规格中的 temperatureCode 必须是 Integer、摄氏单位且有有效 scale/min/max/step；powerCode 必须是 Boolean。未知规格或单位时拒绝控制，不猜测倍率。若设备有多个独立输出，本版每设备只映射一组目标温度/开关；要分别控制多输出需扩展控制映射，不能把整个设备控制误称为单层控制。

## 后端接口

| 功能 | 旧项目 | 独立重构 |
| --- | --- | --- |
| 房间温湿度 | `GET /.netlify/functions/room-environment` | `GET /api/v1/room/environment` |
| 设备规格与状态 | 同上，参数 `?device=设备ID` | `GET /api/v1/room/environment/devices/:id` |
| 手动控制 | `POST /.netlify/functions/room-environment` | `POST /api/v1/room/environment/commands` |

旧项目使用成员 Supabase Bearer 会话，重构使用既有 HttpOnly 会话；均要求 editor/admin，控制提交还验证来源。旧项目控制须配置准确的 SITE_URL（或 Netlify URL）及 SUPABASE_SERVICE_ROLE_KEY，用于服务端写入控制结果；读数不需要服务密钥。

控制请求结构：

```json
{"requestId":"唯一UUID","revision":12,"deviceId":"实际设备ID","action":"temperature","value":28.5}
```

`action=power` 时 value 为布尔值。revision 是读数响应中的房间版本，配置发生变化会拒绝旧版本控制；同一请求号只用于同一内容。同一设备有 60 秒内的 pending 请求时拒绝新的控制；超时后也应先核对设备再决定是否提交新请求。

结果 accepted 仅表示云端接受命令，尚不代表设备执行。unknown/pending 代表结果未确定，应重新查询状态或在 App 核对。failed 是明确未接受或本地检查失败。后台不直接返回涂鸦原始异常、令牌、设备 local_key 等信息。

## 设备绑定前的准备与服务器密钥配置

云项目已开通基础 API 服务不等于设备接口已经验证。现在可先使用后台「温湿度设备 → 涂鸦设备、数据点与控制 → 验证云授权」，或在项目目录运行 `npm run check:tuya`。该检查仅获取云授权，不发送设备控制指令，不要求设备 ID，也不返回密钥或访问令牌。通过只说明云认证成功，设备读取和控制权限要在绑定后验证。

密钥必须配置在实际运行后端的服务器。开发电脑根目录的 `.env` 不会自动同步到线上；也不能把密钥放入网页 JS、前端构建变量或 Git。

```dotenv
TUYA_REGION=cn
TUYA_ACCESS_ID=填写项目的AccessID
TUYA_ACCESS_SECRET=填写最新的AccessSecret
TUYA_DEVICE_IDS=
TUYA_SHADOW_ENABLED=false
TUYA_CONTROL_ENABLED=false
TUYA_CONTROL_MAP={}
```

中国数据中心使用 `cn`；其他数据中心需与项目匹配。设备未绑定时，`TUYA_DEVICE_IDS` 留空即可。

- 旧项目使用 Netlify：将上述变量添加到该站点后端 Functions 的运行环境，重新部署，再到后台验证云授权。
- 重构项目使用 `deploy/migration/compose.yaml`：将变量填入服务器该部署目录的 `.env`。更新应用镜像及 Compose 文件后，在该目录执行 `docker compose up -d api`。该配置只将涂鸦密钥传给 API，不传给 worker。可运行 `docker compose exec api npm run check:tuya` 验证。
- 重构项目使用根目录验证部署：同时加载 `compose.tuya.yaml`，参照现有部署命令保留其他 Compose 参数。
- 直接运行 Node：在启动 API 的服务环境中注入上述变量，重启进程。诊断脚本会读取当前目录 `.env`，现有系统环境变量优先。

后续顺序：A1 在涂鸦智能 App 中绑定并联网 → 在云项目关联该 App 账号并确认设备出现在项目设备列表 → 把实际设备 ID 加入服务器 `TUYA_DEVICE_IDS`（多台逗号分隔）并重启/重新部署 → 后台读取设备规格和状态 → 把实际温度数据点 code 绑定到对应爬柜层。湿度可绑定独立传感器的数据点；未接入前保持未绑定。

读取成功后，再根据 A1 实际返回的规格核对目标温度、开关 code、单位、scale 和安全范围，填写 `TUYA_CONTROL_MAP` 并启用控制。不要照抄其他型号的数据点。当前默认关闭控制。

接口：旧项目 `GET /.netlify/functions/room-environment?check=connection`；重构项目 `GET /api/v1/room/environment/connection`。均要求后台编辑权限。


## A1 数据点核对（2026-10-16 设备调试截图）

截图为「标准指令集 / 设备状态集」。当前通用云适配器已兼容其类型、单位及缩放，无需在代码中写入真实设备 ID。

| 功能 | code | 类型 | 换算/用途 |
| --- | --- | --- | --- |
| 当前温度 | `temp_current` | Integer | `scale=1`，原始值 ÷ 10 得到 ℃；原始范围 0–999 |
| 目标温度 | `temp_set` | Integer | `scale=1`，实际范围 10–45℃，步进 0.1℃ |
| 开关 | `switch` | Boolean | 是否可下发须由 API 的 functions 确认 |
| 锁定 | `auto_lock` | Boolean | 当前项目不提供此控制 |
| 温标切换 | `temp_unit_convert` | Enum | c/f；当前项目不提供温标切换控制 |

后台每层的温度来源选「涂鸦云（A1 智能版）」，设备标识填写服务器白名单中的相应设备 ID，数据通道填写 `temp_current`。不要用 `temp_set` 作为测量温度。截图未提供湿度数据点，湿度保持未绑定，待独立湿度传感器接入。

只读取温度时，服务器配置密钥、区域和 `TUYA_DEVICE_IDS=设备ID1,设备ID2` 即可；`TUYA_CONTROL_ENABLED=false`、`TUYA_CONTROL_MAP={}` 保持原值。部署后先验证云授权，再读取设备核对其规格、状态及实际温度；后台温度单位为 ℃，不得把华氏数据当作摄氏数据绑定。

如果以后启用控制，必须先在实时规格 `functions` 中确认 `temp_set` 和 `switch` 可下发。状态集截图本身不足以证明写权限。服务器映射结构示例（设备 ID 和 20–32℃ 均为示例；实际允许范围由饲养需求确定，不自动采用设备全部 10–45℃ 范围）：

```dotenv
TUYA_CONTROL_MAP={"设备ID1":{"temperatureCode":"temp_set","powerCode":"switch","minC":20,"maxC":32},"设备ID2":{"temperatureCode":"temp_set","powerCode":"switch","minC":20,"maxC":32}}
```

核对映射和允许温度范围后才设置 `TUYA_CONTROL_ENABLED=true`。同一设备绑定多层时控制会影响所有对应层。截图上的调试滑块显示不能代替实时温度读数；真实设备读取、控制尚需服务器联调。


## 统一设备配置与逐层选择（最新界面）

先在「爬房 → 温湿度设备」维护设备名称、来源、设备 ID、温度/湿度通道及有效期。服务器白名单中的设备会自动列出候选，A1 默认预填 `temp_current`；需保存参数才会成为可选设备。没有湿度传感器时湿度通道留空。已有逐层绑定会在保存设备配置时转换为设备列表引用，保持原来的设备和通道。

展开爬柜后，每层右侧显示该层温度与湿度，点击右侧卡片为此层选择设备；上方「层设备」可一次配置全柜各层。允许多层选择同一台设备，温度和湿度可分别选择不同设备。修改设备参数会同步更新所有引用层；删除设备时会解除对应层的引用，界面明确提示。只取消某层选择不删除设备，也不影响其他层。

读数进入爬房时查询一次，「刷新温湿度」手动更新，不进行后台持续轮询。云端值仍标明采样时间未知，失败时不保留旧数值冒充当前温度。

部署要求：旧 Supabase 项目先执行 `052_room_environment_devices.sql`（依赖 050、051），再部署前端。重构项目沿用现有 room_workspace.config JSON 存储，无新增数据库表或 SQL 迁移，部署新版后端与前端即可。密钥和设备白名单仍保存在服务器环境变量中，设备配置只包含非密钥参数。


## Netlify 境外部署与涂鸦中国数据中心排查

涂鸦官方 FAQ 的 Q4 明确说明美国 IP 访问中国数据中心属于跨区调用，禁止跨区 API 与消息订阅：https://github.com/tuya/tuya-home-assistant/blob/main/docs/faq.md 。Netlify Functions 公布的部署区域不含中国大陆：https://docs.netlify.com/build/functions/configuration/#region 。因此境外 Netlify 直接访问中国数据中心是部署兼容性问题；不能靠将 TUYA_REGION 改为 us/eu 解决，设备数据没有随之迁移。后续应将温控后端部署在与设备数据中心匹配的区域，并按涂鸦要求确认整体数据流。

单独的 TUYA_TRANSPORT 不能证明某次失败由地域拦截引起。新诊断在读取失败时区分 TUYA_TIMEOUT、TUYA_DNS、TUYA_TLS、TUYA_CONNECTION、TUYA_NETWORK、TUYA_RESPONSE_FORMAT，并在消息中给出获取令牌/设备信息/规格/状态等失败阶段及固定涂鸦域名。非 JSON 响应附带 HTTP 状态码，不返回响应正文、密钥或令牌。收到涂鸦标准错误响应时继续保留其数字错误码，不推断成地域错误。

控制请求网络失败或结果不明确时仍返回 TUYA_TRANSPORT，审计保持 unknown，不自动重发。此次仅诊断改动，无数据库迁移；部署后点击验证云授权，再读取设备，收集具体错误。没有线上调用结果前不能宣称已验证根因或已恢复读取。
